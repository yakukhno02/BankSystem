# Bank System – Backend застосунок

Цей проєкт - backend-застосунок для простої банківської системи.  
Він демонструє проєктування реляційної бази даних, роботу з транзакціями та реалізацію бізнес-логіки за допомогою Spring Boot і PostgreSQL.

Система дозволяє:
- керувати клієнтами та їхніми рахунками
- виконувати грошові перекази між рахунками
- обробляти транзакції з гарантією цілісності даних
- виконувати аналітичні SQL-запити над банківськими даними

Проєкт виконаний як **курсова робота** з основним фокусом на бази даних, SQL та транзакційність.

## Основний функціонал

### Клієнти (Customers)
- Створення та оновлення клієнтів
- Підтримка м’якого видалення (soft delete)
- Видалені клієнти не зникають з бази, а лише позначаються як неактивні

### Рахунки (Accounts)
- Один клієнт може мати декілька рахунків
- Типи рахунків: CREDIT, SAVING, DEPOSIT
- Баланс рахунку оновлюється транзакційно
- Підтримка soft delete

### Транзакції (Transactions)
- Грошові перекази між рахунками
- Перевірка достатності коштів
- Оновлення балансів у межах однієї транзакції
- Автоматичний rollback у разі помилки

### Картки та кредити
- Банківські картки, прив’язані до рахунків
- Кредити з відстеженням статусу

## Проєктування бази даних

Схема бази даних нормалізована до третьої нормальної форми (3НФ) та включає такі основні таблиці:
- `customer`
- `account`
- `card`
- `transactions`
- `loan`

Основні рішення:
- Для всіх таблиць використовуються первинні та зовнішні ключі
- CHECK-обмеження забезпечують коректність значень
- Унікальні обмеження для критичних полів (email, iban, card_number)
- М’яке видалення реалізоване через поле `is_deleted`

## Транзакційність та бізнес-логіка

Усі критичні бізнес-операції в системі виконуються **в межах транзакцій**.

Для цього використовується анотація `@Transactional` на рівні сервісів.

### Навіщо це потрібно?
- гарантує цілісність даних
- запобігає частковим змінам у базі
- автоматично виконує rollback у разі помилки

### Приклад
Під час грошового переказу:
1. зменшується баланс рахунку-відправника
2. збільшується баланс рахунку-отримувача
3. зберігається запис транзакції

Якщо на будь-якому етапі виникає помилка (наприклад, недостатньо коштів),  
**жодна з операцій не буде збережена**.

## SQL-запити

### Прості запити (SELECT)

У проєкті реалізовано базові запити для отримання даних:

- **Отримати всі рахунки клієнта** (через зв’язок `customer_id`)
- **Отримати транзакції “з” рахунку** (`findByFromAccountId`)
- **Отримати транзакції “на” рахунок** (`findByToAccountId`)
- **Отримати транзакції за типом** (`findByType`)

У цих сценаріях використовуються:
- `WHERE`
- `ORDER BY` (де потрібно)
- прості вибірки з 1–2 таблиць

---

### Аналітичний SQL-запит

Реалізовано **1 аналітичний запит** , який відповідає на бізнес-питання:

**"Які клієнти мають найбільшу активність та обсяг транзакцій?"**

```sql
SELECT
    c.customer_id AS customerId,
    c.name AS name,
    c.surname AS surname,
    COUNT(t.transaction_id) AS transactionCount,
    SUM(t.amount) AS totalAmount,
    AVG(t.amount) AS avgTransactionAmount,
    MAX(t.amount) AS maxTransactionAmount
FROM customer c
         JOIN account a ON a.customer_id = c.customer_id
         JOIN transactions t
              ON t.from_account_id = a.account_id
                  OR t.to_account_id = a.account_id
GROUP BY c.customer_id, c.name, c.surname
ORDER BY totalAmount DESC;
```

Використано JOIN для зв’язку клієнтів, рахунків та транзакцій агрегатні функції:
* COUNT — кількість транзакцій клієнта
* SUM — загальна сума транзакцій
* AVG — середня сума однієї транзакції
* MAX — найбільша транзакція клієнта
* GROUP BY використовується для групування даних по клієнтах
* результати відсортовані за загальною сумою транзакцій у спадному порядку

## Тестування

Основний фокус у проєкті зроблено на **інтеграційних тестах**, які перевіряють реальну роботу з базою даних.

### Інтеграційні тести
- використовують `@SpringBootTest`
- запускаються з профілем `test`
- працюють з in-memory базою **H2**
- кожен тест виконується в транзакції з автоматичним rollback

Перевіряються сценарії:
- створення клієнта та рахунку
- грошові перекази між рахунками
- коректне оновлення балансів
- обробка помилкових сценаріїв

## Docker та запуск проєкту
